# 公共基础约束

## 事实来源

1. 客户工程中的真实源码、制品和依赖版本优先于本 Skill、旧文档和模型记忆。
2. 写代码前核对类名、包名、方法签名、默认值和配置消费位置。
3. 无法从源码确认时明确标为未知，不能编造 API。
4. 当前工程及其构建配置实际引用路径中发现本地 TUIKit Chat 源码时，必须按 [集成](integration.md) 核对它与 GitHub 默认分支最新提交；GitHub 最新提交不会自动覆盖客户当前源码，源码不完全一致或无法确认时先由客户选择。

## 修改边界

1. 使用真实 Chat UI 组件，不用空 Activity、自制假列表、本地假消息或同名 stub 冒充完成。
2. 默认修改宿主 App 和公开扩展点，不为绕过依赖、主题或编译问题修改 Chat UI 内部。
3. 客户确需修改内部源码时，单独列出原因、升级成本和影响文件，并按主 `SKILL.md` 的“结构化提问与等待”重新发起授权。
4. 沿用宿主工程现有 UI 技术栈、导航、主题、状态管理和资源习惯；不要无必要地替换工程技术栈。
5. 只添加当前需求需要的依赖、权限和 Manifest 项。

## 写入与远端操作

凡需客户选择、确认、授权或补充信息，都必须按主 `SKILL.md` 的“结构化提问与等待”主动发起问题；不得只宣告等待或默默停止。

1. 集成、自定义和排障修复：先只读检查，给文件级方案，得到明确授权后才写文件。
2. 创建测试账号和体验消息：先运行不带 `--apply` 的预览，把将创建的内容用大白话告诉客户，得到再次确认后才执行 `--apply`。
3. 方案中的文件、调用或计划创建的账号、好友、群聊、消息发生变化时，重新确认。

## 凭据

- 生产推荐由客户服务端签发 UserSig。
- 客户明确选择参考 Chat Demo 在客户端使用 SecretKey 调试时，可以按其选择实施。
- 必须在方案、写入授权前和最终交付时分别说明：客户端密钥可被提取，不能把该方式描述为安全的生产方案，并继续推荐服务端签发。
- 除客户明确要求写入的目标代码外，不在方案、日志摘要或最终回复中重复完整 SecretKey、管理员 UserSig 或用户 UserSig。
- REST API 创建测试账号和消息时使用管理员 UserSig；客户端登录使用目标用户自己的 UserSig，两者不能混用。

## Android 宿主

- 分别识别宿主 UI 技术栈和客户选择的 Chat UI 版本。客户明确选择优先；未指定时默认 View 版。
- 本地 TUIKit Chat 源码发现范围只包括当前工程及其构建配置实际引用路径，不扫描整个用户主目录；比较 GitHub 版本时不得把宿主仓库身份当成 TUIKit 身份，不在方案授权前改动源码仓库。客户选择 GitHub 最新源码后也必须写入新的独立目录并按已授权方案切换引用，不能原地覆盖当前源码。
- 可以建议 Chat UI 与宿主技术栈保持一致以降低互操作成本，但不能强制客户改选。
- 宿主与 Chat UI 技术栈不一致时，使用 Android 官方互操作方式承载，并在方案中列出容器、生命周期、主题、状态保存、Insets 和导航边界。
- 以所选 Chat UI 的当前源码确认接口：View 版重点核对 `ViewModelStoreOwner`、Activity、Fragment 和 View 生命周期；Compose 版重点核对 Composable 参数、状态、effect、composition 生命周期和导航。
- 互操作只解决承载问题，配置、自定义和页面 API 必须使用所选 Chat UI 版本的真实定义，不能混用两版 API。
- Android Chat 默认同时集成 CallKit，不询问客户是否需要，也不把它作为待选择项；文件级方案仍须如实列出新增模块、依赖、初始化、Manifest 和权限。
- 客户完成集成后明确不需要 Call 时，必须成套删除 CallKit 模块、依赖、初始化及仅供 Call 使用的权限，并隐藏 Chat 中全部语音/视频通话入口。
- `ChatActivity`、会话、联系人、搜索、聊天设置等所有 Chat 页面容器都必须兼容 Edge-to-Edge；宿主已有统一实现时复用并核对，不得重复启用或重复加 Insets。
- Activity 级别使用宿主现有方案或 AndroidX `enableEdgeToEdge()` / `WindowCompat.setDecorFitsSystemWindows(...)`；View 使用 `WindowInsetsCompat` 分配系统栏和刘海屏安全区，Compose 使用对应 Insets padding。
- 明确每个页面的 Insets 负责人。保留原始 padding，不重复累加，不在外层和 Chat 输入组件同时处理 IME。
- 禁止硬编码状态栏、导航栏和刘海区域高度；状态栏和导航栏图标明暗必须跟随当前主题。
- 相机、相册、录音、文件和音视频入口涉及权限时，同时检查 Manifest、运行时权限和能力依赖。
- 会话页始终传完整 `conversationID`，不要把原始 `userID` 或 `groupID` 直接当会话 ID。

## iOS、Flutter、uni-app 等条件支持平台

- 先说明本 Skill 没有该平台的内置 API 基线，并按主 `SKILL.md` 的“结构化提问与等待”询问客户是否继续。
- 客户确认后，从[全功能接入](https://cloud.tencent.com/document/product/269/79075)选择匹配平台、框架、版本和组件形态的官网文档。
- 以官网当前指引、客户锁定依赖和真实源码为准；不得翻译 Android API、Gradle 配置或生命周期规则后套用。
- 仍需先给文件级方案并取得写入授权。官网无匹配方案或工具链不可用时，说明具体限制和替代验证路径，不直接拒绝可完成的部分。

## 验证

1. 使用工程自己的工具链执行目标构建；完整构建不可行时执行可用的静态检查并说明限制。
2. 不启动 App 或模拟器；把运行验证步骤交给客户。
3. 验证失败时保留第一处有效错误和完整上下文，不用 stub 掩盖。
4. 只自动检查本次触及的 SDK 调用；全工程扫描需客户明确要求。
5. Android 集成需静态检查本次新增或修改的所有 Chat 页面容器是否覆盖 Edge-to-Edge 和 Insets；运行效果由客户在高版本系统、手势/三键导航、横竖屏、键盘、刘海屏和浅色/深色主题下验证。
6. 完成说明必须区分：已构建或静态检查、受工具链限制未验证、待客户运行验证、未覆盖能力。
