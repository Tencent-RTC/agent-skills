## 定位

- Android：客户可自由选择 View 或 Compose 版 Chat UI；明确选择优先，未指定时默认 View 版。宿主与 Chat UI 技术栈相匹配更易维护，但不强制。
- iOS UIKit、SwiftUI、Flutter、uni-app 等其他平台：先说明本 Skill 没有该平台的内置 API 基线，并按"结构化提问与等待"询问是否继续；客户确认后，以官网指引和客户工程真实源码为准，继续检查、给方案、修改和执行可行验证。
- Android Chat 默认同时集成 CallKit；默认不询问客户是否需要，也不把它单独说明为可选步骤。客户集成后明确不要 Call 时，再删除依赖与初始化并隐藏 Chat 中全部通话入口。
- 只处理 Chat UI 主链路及其默认 CallKit 接入/移除。Push、Room、生产 UserSig 服务和 Call 深度定制等独立需求先用 [能力边界](references/boundaries.md) 拆分。

## 结构化提问与等待（最高优先级，硬性）

只要后续步骤依赖客户选择、确认、授权或补充信息，就必须优先通过宿主原生结构化提问能力主动发起一个客户可回答的问题；禁止只说"等待确认""请确认后继续"或不提供问题便结束，禁止 AI 默默停下来。任务已经完成、客户明确拒绝或要求停止时可以正常结束。

1. 先检查当前会话实际暴露的宿主工具，不得只根据 IDE 名称猜测，也不得假定固定工具名一定存在。
2. 需要选择、确认、授权或补充信息时，优先调用当前会话实际提供的宿主原生结构化提问工具。以下名称只用于查找线索，只有工具确实已暴露时才能调用：
   - Cursor 常见名称为 `AskQuestion`。
   - Claude Code、CodeBuddy 常见名称为 `AskUserQuestion`。
   - Codex 可能提供 `request_user_input`。
3. 已知名称不存在或对应不上时，禁止立即降级。先检查当前所有宿主内置工具的名称和说明；宿主支持内置工具搜索、延迟工具发现或同类能力时，继续寻找能暂停当前流程并收集用户单选、多选、确认或自由输入的等价原生工具。候选范围只包含宿主内置工具，排除 MCP、第三方远端工具和需要另行安装的工具；本 Skill 的提问流程不得安装、配置、调用或依赖 MCP。
4. 找到等价工具后必须调用，不得用普通正文问题代替；调用前不得先在正文重复同一问题，工具返回前不得执行依赖答案的后续操作。调用报错、超时、返回空结果或不可用时，继续检查剩余宿主内置等价工具；仍无可用工具时按第 6 条降级，不得卡住或默默停止。
5. 每次只问一个问题；选择题提供 2～4 个清晰、互斥、可执行的选项，推荐项放第一位并标明"推荐"，默认单选。需要 userID 等自由文本时，优先使用工具的"其他"或自定义输入能力。
6. 只有检查当前工具和宿主内置工具发现能力后仍找不到等价工具，或者该工具被当前模式、权限、后台任务或非交互环境明确禁止时，才允许降级为普通文字。降级时必须给出一个明确问题和编号选项或输入格式，要求客户直接回复，然后结束当前回合；收到下一条客户回复前不得继续写入或执行依赖答案的操作，不得只宣告正在等待。
7. 已处于宿主原生 Plan 模式时，只有在完整文件级方案展示后触发的原生审批结果才可用于本次授权；进入 Plan、批准高阶计划或切换模式本身不算写入授权。原生审批不能明确表达第 8 条三个结果时，仍按上述规则寻找结构化提问工具。
8. 展示文件级方案后，必须在同一回合发起审批并暂停后续写入：
   - `按此方案执行（推荐）`
   - `调整方案`
   - `暂不执行`
   客户选择"按此方案执行"才算明确授权；跳过、空答案和其他含义不明确的回复均不算授权，必须再次发起可回答的审批。选择"调整方案"或方案内容变化后，重新展示方案并再次发起审批；选择"暂不执行"、明确拒绝或要求停止后正常结束。

## 先检查，再澄清

1. 先从工程读取平台、宿主 UI 技术栈、模块、依赖、已有 Chat 代码、源码或制品、主题与导航；本地源码发现范围只包括当前工程及其构建配置实际引用的本地路径，不扫描整个用户主目录。不要询问可直接查到的信息。
2. 只补问会改变方案的缺失信息，并按"结构化提问与等待"一次只问一个问题。
3. API、类名和配置是否生效必须以客户工程真实源码为准；reference 中的 API 只是最小示例。
4. Android 需分别识别"宿主使用 View 还是 Compose"和"客户选择哪一版 Chat UI"：
   - 客户明确选择 View 或 Compose 时按其选择实施。
   - 客户未指定时默认使用 View 版；可以说明与宿主技术栈匹配通常更省互操作成本，但不能据此强制改选。
   - 宿主与所选 Chat UI 不一致时，使用 Android 官方互操作容器接入，并在方案中列出容器、生命周期、主题、状态和导航成本。
   - 只使用所选 Chat UI 版本的真实 API；宿主技术栈不能作为套用另一版 API 的依据。
5. Android 当前工程及其构建配置实际引用路径中发现 TUIKit Chat 源码时，先读 [集成](references/integration.md) 的"本地 TUIKit Chat 源码版本核对"，比较本地版本与 GitHub 默认分支最新提交；比较完成前不得默认它是最新版。
6. iOS、Flutter、uni-app 等其他平台先读 [能力边界](references/boundaries.md)，说明能力边界并按"结构化提问与等待"询问是否继续：
   - 客户明确选择不继续时停止写入，只提供对应官方入口。
   - 客户确认后，从[全功能接入](https://cloud.tencent.com/document/product/269/79075)选择匹配平台、框架和版本的指引，再按正常方案与授权流程提供帮助。
   - 不得仅因平台不属于 Android 而拒绝，也不得把 Android API 翻译后套用。

## 路由

## 写入授权闸门

集成、自定义和排障修复统一执行：

1. 只读检查工程与真实 API。
2. 输出文件级方案：
   - 目标链路与真实组件
   - 源码核对结果
   - 每个新增或修改文件及目的
   - 依赖、凭据、兼容性和调用风险
   - 发现本地 TUIKit Chat 源码时，列出实际引用路径、源码身份、本地提交或快照结论、GitHub 默认分支最新提交、工作区状态、客户选择、升级或保留方式及回退路径
   - Android 所有 Chat 页面容器的 Edge-to-Edge、系统栏、刘海屏、导航栏和键盘 Insets 处理
   - 编译命令与客户运行验证方式
3. 在同一回合按"结构化提问与等待"发起方案审批；原生审批结果或降级后的客户回复明确授权前不得写入。
4. 授权后才修改代码、编译和检查本次触及的 SDK 调用。

用户最初说"直接改""不用再确认"也只代表启动检查；不能替代看到文件级方案后的明确授权。方案变化后必须重新确认。

## 主动集成

识别到集成意图后，不等用户逐步追问：

1. Android 默认最小链路为登录 → 会话列表 → 聊天页 → 文本消息收发，并同时完成 CallKit 依赖、登录后初始化和 Chat 通话入口；不为 CallKit 单独询问或等待选择。
2. 识别平台；Android 按客户选择处理，未指定 Chat UI 版本时默认 View 版；其他平台按能力边界取得继续确认并找到匹配的官方指引。
3. 发现实际引用的本地 TUIKit Chat 源码时，先完成 GitHub 默认分支最新提交核对；源码不完全一致或无法确认时，按"结构化提问与等待"让客户选择使用 GitHub 默认分支最新源码或保留当前本地源码。该选择只确定方案输入，不能替代文件级写入授权，也不能触发原地更新或覆盖。
4. 主动给出文件级集成方案，并在同一回合按"结构化提问与等待"发起审批。
5. 授权后使用真实 Chat UI 组件实施，不用 stub 冒充。
6. 使用客户工程现有工具执行目标构建或可行的静态检查；失败时转入排障，不绕过真实组件。
7. Android 的 `ChatActivity`、会话、联系人、搜索、聊天设置等所有页面容器必须适配 Edge-to-Edge；不能只处理聊天页，也不能用固定状态栏高度。
8. 按当前平台检查本次触及代码中的空 ID、会话类型、生命周期、失效对象、高频重复调用、分页与节流。
9. 不启动 App 或模拟器；把运行验证步骤交给客户。

客户明确不需要 Call 时，按 [集成](references/integration.md) 的移除流程处理。不得只删除依赖而保留入口，也不得只隐藏入口而保留无用依赖和初始化。

登录链路已经接好，或客户确认登录成功，但聊天页面还没完成时，按"结构化提问与等待"主动只问一次，工具问题文本使用"要不要我帮你创建几个测试账号，再准备一些好友、群聊和消息？等聊天页面接好后就能直接体验。"

最小聊天链路已经完成并可交给客户体验时，按"结构化提问与等待"主动只问一次，工具问题文本使用"要不要我帮你创建几个测试账号，再准备一些好友、群聊和消息？这样你打开 App 就能直接体验聊天。"

根据当前进度二选一，不能两句都问，也不得只把问题写进正文后结束。选项为"现在准备（推荐）"和"暂不准备"。询问时必须使用这种简单表达，不说"造数""灌数据""seed""远端对象""dry-run"等内部术语。客户同意后再读 [体验账号和消息](references/demo-data.md)，先用大白话展示准备创建的内容并按"结构化提问与等待"发起确认；客户拒绝后不继续追问。

客户同意后，预览前必须先确定客户实际用于体验的 Chat userID：

1. 优先从客户已确认的登录结果、登录配置或工程真实代码获取；只能看到变量名或无法确定运行时值时，按"结构化提问与等待"一次只询问一个 userID 问题。
2. 客户已有自己的 Chat userID，或已经使用自己的 userID 登录时，必须以该账号为中心创建测试数据：该账号与两个测试伙伴互为好友、共同加入专属测试群，并生成该账号可直接看到的单聊和群聊消息。不得仍只创建 `demo_alice` 与 `demo_bob` 之间的数据。
3. 只有确认客户没有可用的自有 Chat userID 时，才使用 `demo_alice` 与 `demo_bob` 作为完整体验账号。创建完成后必须继续引导客户，或经授权帮助客户使用其中一个账号登录；不能在客户仍登录其他账号时声称已经可以体验。
4. 实际参与账号或登录账号发生变化时，重新展示本次准备创建的内容，并按"结构化提问与等待"再次发起确认。

## SecretKey 调试

客户明确选择参考 Chat Demo 在客户端使用 SecretKey 调试时，可以实施，不以风险提示阻断：

1. 方案阶段说明客户端密钥可被提取，并推荐生产由服务端签发 UserSig。
2. 请求写入授权前再次提示同一风险。
3. 最终交付时第三次提示风险与生产建议。

不得把这种方式描述为安全的生产方案。
