# 小米 / vivo 上架与通道限制

## 与 MCP 的关系

本文件是 **知识卡**，不拥有独立主链。

- ROUTER `workflow_id`：`troubleshoot-android`
- 关联 flow：`flows/android/vendor-not-received.md`
- 挂载：主要挂 `stage-3` / `stage-6`
- 执行仍走 MCP 状态机；命中本卡后按挂载阶段取证，禁止用本卡替代 `complete_workflow_step`。

## 适用现象

当用户反馈以下任一现象时，优先使用本卡：

- 小米或 vivo 收不到离线推送，回执类似「应用在黑名单」「已关闭 push 通道」。
- 未上架应用市场时厂商通道不可用。
- 其他厂商正常，仅小米或 vivo 失败，且客户端注册看似成功。

不适用于：

- 注册阶段 `registerPush failed` 明确配置错误 → `../../flows/android/vendor-not-received.md`。
- 「只能收到几条」营销限额 → `message-category-limit.md`。

## 共同根因

小米 / vivo 厂商通道通常要求应用完成应用市场上架（或满足厂商对通道开通的条件）；未满足时即使腾讯云侧显示发送尝试，厂商侧也可能拒绝投递。

常见错误模式：

- 用内部测试包期望完整厂商通道体验。
- 将厂商拒绝误判为 TIMPush SDK Bug。
- 未在厂商控制台确认推送开关/应用状态。

## 必须收集的证据

- 应用是否已在小米/vivo 应用市场上架。
- 厂商控制台应用状态与推送开关。
- 厂商回执原文 / 错误码。
- 客户端是否已成功拿到该厂商 token（区分注册成功 vs 投递拒绝）。

## 排查步骤

1. 确认不是包名/证书配错（先走 vendor-not-received 配置核对）。
2. 收集厂商回执文案。
3. 核对上架与厂商控制台通道状态。
4. 向用户说明这是厂商策略，不是客户端少调一个 API 就能绕过。

## 解决方案

- 完成对应应用市场上架并按厂商文档开通推送。
- 在厂商控制台确认应用未关闭 push、未在黑名单。
- 测试阶段可用控制台工具区分「腾讯云已受理」与「厂商拒绝」。
- 无法满足上架条件时，明确产品/业务风险，勿承诺私下通道。

## 验证信号

- 厂商控制台可向该包名下发测试通知。
- 上架且通道开启后，强杀离线推送可达。
