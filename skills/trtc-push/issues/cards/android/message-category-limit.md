# 消息分类与厂商日限额

## 与 MCP 的关系

本文件是 **知识卡**，不拥有独立主链。

- ROUTER `workflow_id`：`troubleshoot-android`
- 关联 flow：`flows/android/vendor-not-received.md`
- 挂载：主要挂 `stage-6-offline-test`（限额/分类）
- 执行仍走 MCP 状态机；命中本卡后按挂载阶段取证，禁止用本卡替代 `complete_workflow_step`。

## 适用现象

当用户反馈以下任一现象时，优先使用本卡：

- 每天只能收到两条/几条，之后收不到，但控制台显示发送成功。
- 厂商回执疑似分类 / 营销限额（工单中偶发 `11043`：**未在 vivo 公开错误码表坐实**，
  仅作弱匹配线索，必须核对回执原文）。
- 更换文案或降低频率后偶尔恢复。

不适用于：

- 完全从未收到（优先注册/证书问题）→ `../../flows/android/vendor-not-received.md`。
- 单次送达不弹且无「日限额」特征 → `../../flows/android/delivered-not-displayed.md`。

## 共同根因

国内厂商对推送有消息分类；默认常落入营销/运营类并有严格日限额。未申请即时通信/私信等合适分类，或未在控制台/API 填写 category/模板时，会出现「前几条成功、之后静默失败」。

常见错误模式：

- 把限额当成 SDK 随机丢消息。
- 只改客户端，不申请厂商分类/模板。
- 控制台默认分类与 REST 覆盖字段不一致。

## 必须收集的证据

- 一天内成功触达条数与失败起始时间。
- 控制台证书页默认 category / 分类配置。
- REST/客户端是否传分类字段。
- 厂商错误码 / 回执原文（如有）。若只有 `11043` 而无公开文档对照，标注为疑似，
  优先按分类限额现象链排查，勿写成官方确定码义。

## 排查步骤

1. 确认注册与证书基本正确（能收到前几条）。
2. 核对是否符合「限额」时间模式。
3. 对照消息分类文档检查申请与字段。
4. 区分测试额度用尽 vs 正式分类未开通。

## 解决方案

- 按[推送消息分类](https://cloud.tencent.com/document/product/269/100649)申请并适配厂商分类。
- 在控制台设置默认分类；需要多种分类时用 REST/客户端字段覆盖。
- 向用户说明生效可能有延迟，且各厂商规则不同。
- 产品无法突破的厂商硬限额 → 解释并升级商务/厂商，不假装客户端可修。

## 验证信号

- 同类消息在原「限额」之后仍可持续触达。
- 厂商侧分类展示为已申请的通道类型。
