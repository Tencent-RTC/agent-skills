# 源码变更配方

仅新增公共 API/配置、跨文件功能、内部缺陷修复时读取。简单 App 配置请走 app 路径；已有源码修改授权不因本页再次索取同范围授权。

## 配方 A：新增一个公开配置项

以消息输入或消息列表为例，按真实链逐层检查；不存在的转换层不要强造：

1. 在具体公开 Config 定义增加可选覆盖存储（一般 `userXxx`）；保留值/引用类型与现有命名风格。
2. 在公开 init 增加带默认值参数并赋值；优先末尾增参，避免破坏现有 Swift 参数顺序/调用源码兼容。
3. 在 Defaults/配置扩展增加 getter/setter和缺省值；查缺省来自常量还是 AppBuilder，不只改一份初始化值。
4. 检查 internal config protocol/conformance/解析是否需要新增成员；结构体原生就符合协议时不再加冗余适配层。
5. 在真正构建/刷新 UI 的消费者使用它：按钮、菜单、约束、cell bind/高度计算可能分布在不同文件。
6. 查看 Page façade 是否传透，以及 PageImpl 是否会创建特殊配置或重写值。例：ChatPage隐式右头像为true，而显式空config为false。新增列表/输入协议成员还需核对 `components/chatbot/ChatbotMessageListConfig.swift` 和 `ChatbotMessageInputConfig.swift` 的base透传/特殊覆盖；协议有默认实现时，漏透传可能编译通过但行为丢失。
7. 如果要求 `appConfig.json`，另接 JSON decode → AppBuilder属性 → getter缺省 → UI消费者；仅增加JSON键不算功能完成。
8. 用同一配置验证未传参数、传true、传false、页面复建/复用、单群聊/机器人等特殊配置；兼容旧构造调用。
9. 修改 public API 后做 App侧普通 `import TUIChatKit` typecheck，不使用 `@testable` 掩盖访问级别。只给编译器看的测试 façade 不能冒充真实依赖验证。

## 配方 B：修改布局/样式

先确认是否已有公开开关/appearance；源码任务可以修改实现但默认行为保持可解释。找到约束创建、动态更新和高度/缓存计算三个点。气泡外框与内容内边距、消息行与avatar/nickname可能不同层。

修改前读取实际config值和UI状态；改后回归长短文本、多行、异步图片、自定义消息、左右/自己对方、多选、深浅色、RTL。不得只改一次 `init`，忽略复用后的 `bind` 和异步尺寸失效。

## 配方 C：新增动作/状态

区分“显示入口”和“执行动作”。追踪回调是否由宿主注入或内部消费，确认ID与权限；新按钮不应只有外观没有处理者。

动作成功以Store结果/状态更新为准，失败恢复乐观UI；取消/离开页面后拒绝迟到结果。首载用真实查询或当前state，不能用空列表推断默认状态。新增枚举检查格式器、菜单、角标等所有相关消费者，不能只把它转换成bool。

## 配方 D：修改跨层逻辑

- 先指出是 TUIChatKit、AtomicXCore 还是 IM SDK 行为。
- 有UI源码但Core是二进制：只能修改UI对公开Core动作/状态的使用，不编辑 `.swiftinterface` 伪造实现。
- Core源码确实参与构建：核对API定义、Impl override、SDK类型转换、SDK回调到state更新；不要忽略多实例Store共享状态问题。
- SDK协议/服务端限制未知：给出证据缺口，不把产品猜测写成确定约定，不用UI本地“成功”覆盖错误。

## 修改闭环

在实际编辑前能回答以下五项，就停止无关探索：

| 问题 | 所需证据 |
| --- | --- |
| 请求从哪里进来？ | 页面事件、配置或动作处理函数 |
| 谁持有状态？ | Config/Store/局部状态/宿主 |
| 哪处真正消费？ | bind/render/约束/服务调用 |
| 还会影响谁？ | 同字段/枚举/事件的相关消费者 |
| 如何判定成功且不回归？ | 模块最小回归与可行构建目标 |

只变更必要文件，不自动改另一平台。新文件需确认podspec glob或Xcode source membership；改头文件/public接口还需检查对外编译。保持资源和多语言配套，新增开关不得只在demo展示却未进入产品源码。

## 验证顺序

1. 精确diff与lint：排除无关改动，确认实际源码引用。
2. 与目标依赖匹配的类型检查/单元测试；public API用外部模块。
3. 可行时构建实际 Pod/App目标，配置和scheme由当前工程取得，不写死旧例子。若XcodeGen/Tuist等重新生成宿主xcodeproj并覆盖CocoaPods接线，执行顺序为生成工程 → pod install（使用现有锁文件）→ 打开/构建workspace；先生成后装Pod，不能反过来用生成覆盖集成结果。纯源码编辑不要求重装Pods。不要因产物存在就当它是本轮构建。
4. 按主模块指南运行UI回归（需设备/账号授权），真实消息或群动作另确认副作用。
5. 交付“改了哪些消费者、缺省是否变化、成功/失败/取消路径、已验证/未验证”；同时说明仍需SDK或服务端确认的事项。

用户环境不能构建时保留最小验证办法并诚实报告，不以stub、删依赖、禁用功能换取表面成功。
